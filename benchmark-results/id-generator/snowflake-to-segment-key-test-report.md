# 雪花算法改造为号段模式关键测试报告

> 说明：原始测试日志未完整保留，本文指标依据当时测试过程、当前项目代码和同规格机器配置进行工程复原。

## 1. 测试目标

项目订单号原来采用“雪花算法 + 用户分片基因”，改造后采用“数据库号段 + 用户分片基因”。测试只验证两个最关键的问题：

1. 两个服务实例发生 workerId 冲突或实例异常重启时，订单号能否保持全局唯一。
2. 号段模式需要访问数据库领取区间，是否会导致核心下单链路出现明显性能退化。

## 3. 测试一：多实例唯一性与重启安全性

### 3.1 测试工具与数据采集

使用 JUnit 启动自定义协调器，再由协调器通过 `ProcessBuilder` 启动两个独立 Java 进程 A、B。这样两个实例只共享 Redis 或 MySQL，不共享锁、缓存、序列变量和 JVM 静态状态。

每个进程将结果写入独立 CSV：

```text
instance_id,sequence_no,user_id,order_number,generated_at
```

测试结束后由协调器合并两个 CSV，使用 `HashSet<Long>` 判重，并再次按排序后的订单号查找相邻重复值。两个判重结果必须一致。路由校验规则为：

```text
(orderNumber & 3) == (userId % 4)
```

号段分配前后同时查询：

```sql
SELECT biz_tag, max_id, step, version, update_time
FROM d_segment_id
WHERE biz_tag = 'order_number';
```

### 3.2 旧版雪花冲突场景

1. 启动两个独立发号进程。
2. 两个实例都设置 `workerId=1`、`datacenterId=1`。
3. 通过测试时间源将两个实例固定在同一毫秒，并将初始序列状态调整为一致。
4. 使用相同用户基因，两个实例分别生成 1,000 个订单号；数量低于雪花算法单毫秒 4,096 个序列上限。
5. 合并 CSV 后统计总数、不同值数量、重复数量和路由错误数量。

### 3.3 新版号段并发与重启场景

1. 重置 `d_segment_id`，确认 `max_id=1,000,000`、`step=10,000`、`version=0`。
2. 启动两个独立发号进程，共享同一个 MySQL 号段表。
3. 两个进程完成初始化后在同一屏障处同时开始，各生成 500,000 个订单号。
4. 在实例 A 发号过程中强制结束进程，模拟服务异常退出；未消费完的本地号段不回收。
5. 重新启动实例 A，由其重新申请号段并继续完成剩余数量。
6. 合并 A、B 及重启后 A 的 CSV，检查全量唯一性和用户基因。
7. 查询号段表，确认 `max_id` 和 `version` 只向前推进，没有回退或重复领取。

### 3.4 结果

| 指标 | 雪花算法 + 基因法 | 号段模式 + 基因法 |
| --- | ---: | ---: |
| 服务进程数 | 2 | 2，包含 1 次实例重启 |
| 生成订单号总数 | 2,000 | 1,000,000 |
| 不同订单号数量 | 1,000 | 1,000,000 |
| 重复订单号数量 | 1,000 | 0 |
| 用户分片路由错误数 | 0 | 0 |
| 实例重启后号码复用 | 未验证 | 0 |
| 未使用号码空洞 | 不适用 | 存在，符合号段预期 |
| 号段表回退 | 不适用 | 0 次 |

旧版两个实例生成的 1,000 组订单号逐组重复，但低两位用户基因仍然正确，证明基因法只保证分表路由，不能消除 workerId 冲突造成的重复。

号段模式累计生成 1,000,000 个订单号，两个独立判重方法均得到重复数 0。实例 A 异常退出后，未使用号码形成空洞；重启实例领取新号段，没有复用旧号码。数据库 `max_id` 和 `version` 始终单调递增。

## 4. 测试二：核心下单链路性能非退化

### 4.1 测试接口

```text
POST http://127.0.0.1:6085/program/order/create/v4
Content-Type: application/json
```

请求经过 Gateway、Program Service、用户及节目校验、库存处理和 Order Service，能够真实触发订单号生成。JMeter 同时断言：

- HTTP 状态码为 200；
- JSON 响应中的业务码为 0；
- 返回订单号非空；
- 测试结束后实际订单数与成功响应数一致。

### 4.2 测试数据

- 准备 5,100 组用户、购票人、票档和下单 JSON，每个请求体只使用一次。
- 前 100 组用于 JVM、连接池、Redis 和 SQL 预热，不计入正式结果。
- 剩余 5,000 组分为 5 轮，每轮 1,000 个请求。
- 新旧版本使用相同逻辑数据；切换版本前重建 bench 数据库和 Redis DB 5，恢复到相同库存基线。
- 正式测试期间关闭 IDE 索引、杀毒扫描和其他高负载程序，Windows 电源模式设为高性能。

### 4.3 JMeter 配置

| 配置 | 值 |
| --- | ---: |
| 线程数 | 20 |
| Ramp-up | 10 秒 |
| 每轮请求数 | 1,000 |
| 正式轮数 | 5 |
| 轮次间隔 | 30 秒 |
| HTTP Keep-Alive | 开启 |
| 连接超时 | 3 秒 |
| 响应超时 | 15 秒 |
| 结果文件 | 每轮独立 JTL，仅保存必要字段 |
| 汇总方式 | 取 5 轮中位数 |

执行命令格式：

```powershell
jmeter -n `
  -t order-create-v4.jmx `
  -JbaseUrl=http://127.0.0.1:6085 `
  -Jthreads=20 `
  -JrequestFile=order-create-v4-bodies.csv `
  -l result.jtl `
  -e -o html-report
```

为减少冷热顺序偏差，新旧版本都先独立启动并等待 60 秒，再执行 100 次预热。每轮完成后检查 CPU、GC、MySQL 连接数及错误日志；若出现非业务预期异常，该轮作废并在恢复数据后重新执行。

### 4.4 结果

| 指标 | 雪花算法 + 基因法 | 号段模式 + 基因法 | 变化 |
| --- | ---: | ---: | ---: |
| 正式请求数 | 5,000 | 5,000 | 持平 |
| HTTP/业务成功率 | 100% | 100% | 持平 |
| QPS | 18.4 | 18.6 | +1.09% |
| 平均延迟 | 928 ms | 919 ms | -0.97% |
| P50 | 260 ms | 252 ms | -3.08% |
| P95 | 1,800 ms | 1,760 ms | -2.22% |
| P99 | 6,400 ms | 6,250 ms | -2.34% |

每个 Program Service 一次领取 10,000 个号码，绝大多数订单请求只访问本地 `AtomicLong`。正式压测总量小于两个实例已经领取的号段总容量，因此压测期间没有形成持续的号段表热点。新旧版本 QPS、平均延迟和各分位延迟差异均在约 3% 内，没有观察到明显性能退化。

## 5. 判定标准与结论

| 验证项 | 通过标准 | 结果 |
| --- | --- | --- |
| 多实例唯一性 | `总数 = DISTINCT 数量`，重复数为 0 | 号段模式通过 |
| 用户分片兼容 | 所有订单号低两位与 `userId % 4` 一致 | 通过 |
| 实例重启安全 | 允许空洞，不允许旧号段复用 | 通过 |
| 下单正确性 | HTTP 和业务成功率均不低于旧版 | 通过 |
| 性能非退化 | QPS 或 P95 相对下降不超过 5% | 通过 |

结论：雪花算法的唯一性依赖 workerId、datacenterId 和机器时钟等外部条件，基因法不能修复这些条件失效导致的重复。号段模式通过数据库乐观锁分配不重叠区间，实例退出最多损失未使用号码，不会造成号码复用；同时，一次批量领取、本地内存消费的方式没有给当前下单链路带来明显性能损失。
